# Redis 기반 랭킹 및 비동기 쿠폰 설계 보고서

본 문서는 이커머스 시나리오에서 **Redis를 활용한 인기 상품 랭킹 시스템**과, 선택 과제로 수행한 **Redis 기반 비동기 선착순 쿠폰 발급 시스템**에 대한 설계 의도, 구현 방식, 그리고 개발 후 회고를 정리한 보고서이다.

---

## 1. 과제 개요

### 1.1 Redis 기반 인기 상품 랭킹

* 요구사항

    * 가장 많이 주문된 상품을 기준으로 Top-N 랭킹 제공
    * 트래픽 증가 시에도 조회 성능이 안정적으로 유지될 것

### 1.2 [선택] 비동기 선착순 쿠폰 발급

* 요구사항

    * 동시에 다수의 쿠폰 발급 요청이 들어와도 정확히 1회만 발급
    * 중복 발급 및 초과 발급 방지
    * Redis를 활용한 동시성 제어

---

## 2. Redis 기반 인기 상품 랭킹 설계

### 2.1 문제 정의 (Why)

기존 DB 기반 랭킹 방식은 다음과 같은 한계를 가진다.

* 주문 테이블 기준 `GROUP BY + ORDER BY` 쿼리 비용 증가
* 랭킹 조회 빈도가 높을수록 DB 부하 집중
* 실시간 랭킹 제공이 어려움

따라서 **정렬과 Top-N 조회에 특화된 Redis 자료구조를 랭킹의 소스로 활용**하는 설계를 채택했다.

---

### 2.2 핵심 설계 결정

#### 1) Redis Sorted Set(ZSET)을 랭킹의 Source of Truth로 사용

* Key

    * `rank:product:top-selling:all:v1`
* Member

    * `productId`
* Score

    * 누적 주문 수량

#### 2) 랭킹 갱신은 주문 트랜잭션과 분리 (Outbox 기반)

* 주문 생성 시 DB 트랜잭션에서는 **주문 + Outbox 이벤트만 커밋**
* 별도의 Consumer가 Outbox 이벤트를 소비하여 Redis ZSET을 업데이트

이를 통해:

* DB 트랜잭션의 안정성 확보
* Redis 장애가 주문 성공에 직접 영향을 주지 않도록 분리

---

### 2.3 처리 흐름

1. 주문 생성 및 결제 완료
2. OrderCreated 이벤트를 Outbox 테이블에 저장
3. `PopularProductConsumer`가 Outbox 이벤트를 주기적으로 조회
4. 이벤트 payload의 상품 목록을 순회하며

    * `ZINCRBY rank:product:top-selling:all:v1 quantity productId`
5. 랭킹 조회 API는 Redis ZSET에서 Top-N 조회 후 상품 상세를 DB에서 조회

---

### 2.4 구현 요약

* **쓰기 경로**

    * Outbox Consumer → Redis ZSET (`ZINCRBY`)

* **읽기 경로**

    * Redis ZSET (`ZREVRANGE`) → Product DB 조회

* DB 기반 랭킹 테이블 및 주기적 Cache Refresh 로직 제거

## 3. [선택] Redis 기반 비동기 선착순 쿠폰 발급 설계

### 3.1 문제 정의 (Why)

선착순 쿠폰 발급 기능은 다음과 같은 경쟁 조건을 가진다.

* 다수의 사용자가 동시에 쿠폰 발급 요청
* 동일 사용자의 중복 발급 방지
* 발급 수량 초과 방지

DB 트랜잭션만으로 처리할 경우:

* 락 경쟁 심화
* 동시성 테스트에서 중복/초과 발급 발생 가능

---

### 3.2 핵심 설계 결정

#### 1) Redis를 이용한 1차 동시성 제어

Redis를 **진입 제어 레이어**로 사용하고, 최종 정합성은 DB가 보장하도록 설계하였다.

* Redis Keys

    * `coupon:{couponId}:remain` : 남은 수량 (String)
    * `coupon:{couponId}:issued` : 발급된 사용자 집합 (Set)

#### 2) Lua Script를 통한 원자적 검증

하나의 Redis Script에서 다음을 원자적으로 수행한다.

1. 이미 발급된 사용자 여부 확인
2. 잔여 수량 확인
3. 수량 차감 및 발급 사용자 등록

Redis Script 결과에 따라:

* 성공 → DB 트랜잭션 진행
* 실패 → 즉시 예외 반환

---

### 3.3 처리 흐름

1. 클라이언트 쿠폰 발급 요청
2. Redis Lua Script 실행

    * 성공 시에만 다음 단계 진행
3. DB 트랜잭션에서 UserCoupon 저장
4. 트랜잭션 커밋 완료

> Redis는 **선착순 진입 제어**, DB는 **최종 발급 이력의 Source of Truth** 역할

---

## 4. 테스트 전략

### 4.1 랭킹 시스템 테스트

* Outbox 이벤트 소비 후 Redis ZSET 점수 증가 검증
* 랭킹 조회 시 Top-N 순서 보장 여부 확인
* 테스트 간 Redis 데이터 격리를 위해 랭킹 Key 삭제

### 4.2 쿠폰 동시성 테스트

* 다중 스레드 환경에서 동시 발급 요청
* 성공 1건, 실패 N-1건 검증
* Redis 초기화 누락 시 테스트 실패 경험 → 테스트 격리의 중요성 확인

---

## 5. 개발 회고 (Retrospective)

### 5.1 Redis를 캐시가 아닌 "도메인 도구"로 인식하게 된 계기

* 단순 Cache Refresh 구조에서는 Redis의 장점을 체감하기 어려웠음
* ZSET, SET, Lua Script를 활용하면서

    * 정렬
    * 중복 방지
    * 원자 연산
      을 도메인 문제 해결에 직접 활용할 수 있음을 이해하게 됨

### 5.2 Outbox + Redis 조합의 중요성

* Redis를 DB 트랜잭션 내부에 직접 결합할 경우

    * 장애 전파
    * 정합성 붕괴 위험
* Outbox를 경계로 두면서

    * 비동기 처리
    * 재시도 가능성
    * 장애 격리
      를 자연스럽게 달성할 수 있었음

### 5.3 테스트에서 배운 점

* Redis는 상태를 가지므로 테스트 격리가 매우 중요
* DB만 초기화하고 Redis를 초기화하지 않으면

    * 테스트 결과가 비결정적이 됨
* 통합 테스트 환경에서 Redis 초기화 전략을 명확히 가져가야 함을 체감

---

## 6. 결론

본 과제를 통해 Redis를 단순한 캐시 저장소가 아닌,

* 랭킹 계산
* 동시성 제어
* 비동기 이벤트 처리

에 적극적으로 활용하는 설계를 경험했다.

특히 **Redis + Outbox + DB 트랜잭션의 역할 분리**는,
실제 이커머스/대규모 트래픽 환경에서도 확장 가능한 구조임을 학습할 수 있었다.
