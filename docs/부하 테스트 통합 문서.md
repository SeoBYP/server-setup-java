## 부하 테스트 통합 문서 (k6 기준)

### 1. 목적
- **성능**: 피크/스파이크 트래픽에서 `RPS`, `p95/p99`, `에러율`을 측정하고 병목을 식별한다.
- **정합성**: 동시성 상황에서 아래 불변조건을 검증한다.
    - 주문: **중복 주문 방지(멱등키/락)**
    - 재고: **과차감(음수/초과 판매) 없음**
    - 지갑: **음수 잔액 없음**
    - 쿠폰: **초과 발급 0 / 유저 중복 발급 0**
- **구성요소 관점**: Redis 분산락 경합, DB 트랜잭션 경합, 쿠폰 발급의 **동기 대기(최대 3초)**로 인한 타임아웃(504) 거동을 확인한다.

---

### 2. 테스트 대상 API(코드 기준 확정)

#### 2.1 주문
- `POST /api/v1/orders`
    - Body 필드: `userId`, `items[{productId, quantity}]`, `userCouponId?`, `idempotencyKey`

#### 2.2 지갑
- `POST /api/v1/wallets/{userId}/charge` (Body: `amount`)
- `POST /api/v1/wallets/{userId}/debit` (Body: `amount`)
- `GET  /api/v1/wallets/{userId}/balance`

#### 2.3 상품
- `GET /api/v1/products`
- `GET /api/v1/products/{productId}`
- `GET /api/v1/products/top-selling`

#### 2.4 쿠폰
- `POST /api/coupons/claim/{couponId}`
    - 성공/실패 상태코드가 구분됨: **200 / 409 / 403 / 410 / 504**
- `GET  /api/coupons/users/{userId}/coupons`

> 주의: 쿠폰 API만 `/api/v1`이 아니라 `/api/coupons` 경로를 사용한다.

---

### 3. 테스트 시나리오(Endpoint × 목적 × 패턴 × 합격기준)

| ID | 시나리오 | Endpoint | 트래픽 패턴(k6) | 합격기준(예시) | 정합성 검증 |
|---|---|---|---|---|---|
| S1 | 주문 스텝업(기본 처리량) | `POST /api/v1/orders` | 20→50→100 RPS, 각 10분 | p95 < 800ms, 에러율 < 1% | 성공 주문 수만큼만 재고/잔액 반영 |
| S2 | 주문 핫상품 경합 | `POST /api/v1/orders` | 단일 상품 집중 100→200 RPS, 15분 | p95 < 1200ms, 에러율 < 2% | 성공 주문 수 ≤ 재고, 재고 음수 0 |
| S3 | 주문 멱등 검증 | `POST /api/v1/orders` | 동일 `userId` + 동일 `idempotencyKey`로 50 RPS, 5분 | 중복 주문 0 | 동일 키에 대해 주문 1건만 생성 |
| S4 | 쿠폰 스파이크(선착순) | `POST /api/coupons/claim/{couponId}` | 0→500 RPS(5초) + 30초 유지 | 504 비율 추적(권장 < 5%), p95 < 1500ms | 성공 발급 수량 초과 0, 유저 중복 발급 0 |
| S5 | 쿠폰 적체(장시간) | `POST /api/coupons/claim/{couponId}` | 100 RPS, 10~20분 | 504/5xx 추세 분석 | 실패 사유 분포(409/410/403/504) |
| S6 | 지갑 차감 경합 | `POST /api/v1/wallets/{userId}/debit` | 동일 userId 100 RPS, 10분 | p95 < 500ms, 에러율 < 1% | 잔액 음수 0, 기대 잔액 일치 |
| S7 | 상품 조회 부하 | `GET /api/v1/products*` | 300~800 RPS, 10분 | p95 < 200~300ms | 에러율 < 0.5% |

> 합격기준의 수치는 “과제/실습용 기본값”입니다. 환경(로컬/단일VM/컨테이너/DB사양)에 맞춰 조정하세요.

### 4. 테스트 데이터/입력 규칙

#### 4.1 주문 요청 바디 예시
```json
{
  "userId": 1,
  "items": [
    { "productId": 1, "quantity": 1 }
  ],
  "userCouponId": null,
  "idempotencyKey": "<IDEMPOTENCY_KEY>"
}
```


- **S1/S2**: `idempotencyKey`는 요청마다 다르게 생성
- **S3**: `userId` 고정 + `idempotencyKey` 고정

#### 4.2 쿠폰 발급 요청 바디 예시
```json
{
  "couponId": 1,
  "userId": 123,
  "requestId": "<REQUEST_ID>"
}
```

- 스파이크에서는 `userId`를 1..N 범위로 분산(중복발급 검증 용이)
- 409/410/403/504는 “예상 가능한 결과”일 수 있으므로 **분포 관찰이 핵심**

---

### 5. 관측 지표(보고서 필수 항목)

#### 5.1 k6 결과(필수)
- `http_req_duration` p50/p95/p99
- `RPS`(요청률), 성공률/실패율(`status code`별)
- 시나리오별 TPS 비교(스텝업 구간별)

#### 5.2 시스템 지표(가능하면)
- 애플리케이션: CPU, 메모리, GC, 쓰레드, DB 커넥션 풀 대기
- DB: 슬로우쿼리, 락 대기, 커넥션 수
- Redis: ops/sec, latency, connected clients
- 쿠폰 관련: (가능 시) Kafka 컨슈머 처리율/지연(504 증가와 상관관계)

---

### 6. 실행 절차(권장 순서)
1. **S7 상품 조회**로 베이스라인(시스템/네트워크 정상 확인)
2. **S1 주문 스텝업**으로 처리량/지연 곡선 확보
3. **S2 핫상품 경합**으로 락/경합 상황 유도
4. **S3 멱등**으로 중복 주문 방지 검증
5. **S6 지갑 경합**으로 음수 잔액 방지 검증
6. **S4 쿠폰 스파이크**, **S5 장시간**으로 타임아웃/분포 분석

---

### 7. 정합성 검증 체크리스트(테스트 후)
- 주문:
    - 동일 `idempotencyKey`에 대해 **주문 1건만** 생성됐는가
    - 성공 주문 수만큼만 재고/지갑이 변했는가
- 쿠폰:
    - 발급 성공 건수가 **총 발급 가능 수량을 초과하지 않는가**
    - 동일 유저가 중복 발급되지 않았는가(409 발생과 함께 확인)
- 지갑:
    - 잔액 음수 0건
    - 최종 잔액이 기대값과 일치

---

### 8. k6 스크립트 작성 가이드(문서 수준 요약)
- executor는 다음처럼 선택:
    - **RPS를 목표로 제어**: `ramping-arrival-rate`, `constant-arrival-rate`
- 쿠폰은 3초 대기 특성이 있으므로:
    - `504(Gateway Timeout)`를 별도 카운트로 집계
    - 409/410/403은 실패로만 보지 말고 **비즈니스 결과로 분류**해 분석
