# 카프카 구조 및 동작 정리.md

## 1. Kafka란 무엇인가?

**Kafka는 대규모 트래픽 환경에서 “이벤트(메시지)를 안전하고 빠르게 전달하기 위한 분산 메시징 시스템”**이다.

단순히 “메시지 큐”라고 이해하면 반은 맞고 반은 틀리다.
Kafka의 핵심 가치는 다음 3가지다.

* **대량 처리량 (High Throughput)**
* **메시지 유실 방지 (Durability)**
* **서비스 간 결합도 제거 (Loose Coupling)**

### Kafka가 등장한 배경

기존 방식의 문제:
* DB 트랜잭션 안에서 외부 시스템 호출
* Application Event (메모리 기반 이벤트)
* 동기 API 연쇄 호출

➡️ **트래픽 증가 + 장애 발생 시 전체 서비스가 같이 무너짐**

Kafka는 이 문제를 해결하기 위해 등장했다.

## 2. Kafka 핵심 개념 정리

### 2.1 Producer (생산자)

* **메시지를 생성해서 Kafka로 보내는 주체**
* 예: 주문 서비스, 결제 서비스

```text
주문 완료 → Producer가 "주문완료 이벤트"를 Kafka에 발행
```

**중요 포인트**

* Producer는 **Consumer가 누구인지 모른다**
* “Kafka에만 잘 넣으면 내 역할은 끝”

👉 **이게 서비스 결합도를 끊는 핵심 포인트**

---

### 2.2 Topic (토픽)

* 메시지를 분류하는 **논리적 카테고리**
* 예:

    * `order-created`
    * `payment-completed`
    * `coupon-issued`

```text
"주문 완료 이벤트"는 order-completed 토픽으로
"쿠폰 요청 이벤트"는 coupon-request 토픽으로
```

👉 **이벤트의 종류 = Topic**

---

### 2.3 Partition (파티션)

* Topic을 구성하는 **물리적 저장 단위**
* Kafka의 **성능과 확장성의 핵심**

#### 왜 Partition이 중요한가?

* 파티션 개수 = **병렬 처리 가능 개수**
* 파티션 내부에서는 **메시지 순서가 보장됨**

```text
Topic: order-completed
 ├─ Partition 0
 ├─ Partition 1
 └─ Partition 2
```

**핵심 규칙**

* ❌ Topic 전체 순서 보장 안 됨
* ✅ **같은 Partition 안에서는 순서 보장**

---

### 2.4 Message Key (키)

* 메시지가 **어느 파티션으로 갈지 결정하는 기준**
* 보통 **비즈니스 식별자(ID)**를 사용

```text
key = orderId
→ 같은 orderId는 항상 같은 Partition
→ 순서 보장
```

❗ **이걸 안 하면 생기는 문제**

* 같은 주문 이벤트가 서로 다른 파티션으로 흩어짐
* 순서 깨짐
* 동시성 버그 발생

---

### 2.5 Consumer (소비자)

* Kafka에서 메시지를 **읽어가는 주체**
* 보통 “이벤트를 처리하는 서비스”

예:

* 알림 서비스
* 데이터 분석 서비스
* 쿠폰 발급 서비스

---

### 2.6 Consumer Group

* **같은 목적을 가진 Consumer들의 묶음**
* 하나의 파티션은 **같은 Consumer Group 안에서 오직 하나의 Consumer만 처리**

```text
Topic: order-completed
Consumer Group: payment-service
 ├─ Consumer 1 → Partition 0
 ├─ Consumer 2 → Partition 1
 └─ Consumer 3 → Partition 2
```

**의미**

* Consumer Group = 하나의 서비스
* 서비스 단위로 확장 가능

---

### 2.7 Offset (오프셋)

* Consumer가 **어디까지 메시지를 처리했는지 기록하는 위치값**

```text
Partition 0:
[0] [1] [2] [3] [4]
            ↑
         current offset
```

**왜 중요한가?**

* 장애 발생 시:

    * 마지막 처리 위치부터 다시 읽기 가능
* 최소 한 번 처리(At-least-once) 보장

## 3. Kafka 데이터 흐름 (Producer → Topic → Partition → Consumer)

### 전체 흐름 요약

```text
1. Producer가 메시지를 생성
2. Topic으로 전송
3. Key 기반으로 Partition 선택
4. Kafka Broker에 디스크 저장
5. Consumer가 Poll
6. 처리 완료 후 Offset Commit
```

### 단계별 상세 설명

#### 1️⃣ Producer → Topic

* Producer는 Topic 이름만 알고 전송
* Consumer 존재 여부는 신경 쓰지 않음

👉 **비동기, 느슨한 결합**

---

#### 2️⃣ Topic → Partition

* Key가 있으면: `hash(key) % partitionCount`
* Key가 없으면: Round-Robin

👉 **순서가 중요한 이벤트는 반드시 Key 설정**

---

#### 3️⃣ Partition → Consumer

* Consumer Group 내에서 파티션을 분배
* 병렬 처리 가능

---

#### 4️⃣ Offset Commit

* Consumer가 “여기까지 처리 완료”라고 Kafka에 알림
* 장애 발생 시 재처리 가능

---

## 4. Kafka의 장점

### 4.1 성능 & 확장성

* 초당 수십만~수백만 메시지 처리
* Broker / Partition 추가로 **수평 확장**

---

### 4.2 메시지 유실 방지

* 디스크 기반 저장
* Replication 지원
* 장애 발생해도 메시지 유지

👉 Application Event와의 결정적 차이

---

### 4.3 서비스 간 결합도 제거

* Producer ↔ Consumer 완전 분리
* Consumer 장애가 Producer에 영향 없음

---

### 4.4 재처리 가능성

* Offset 조정으로 과거 이벤트 재처리 가능
* 데이터 분석, 장애 복구에 매우 중요

---

## 5. Kafka의 단점 (현실적인 이야기)

### 5.1 운영 복잡도

* 클러스터 구성
* 모니터링
* 파티션/리밸런싱 관리

👉 **소규모 서비스에는 과함**

---

### 5.2 Exactly-Once가 기본 아님

* 기본은 At-least-once
* 멱등성 설계 필요

```text
같은 메시지 2번 와도
결과는 1번만 반영되도록
```

---

### 5.3 실시간 요청-응답에는 부적합

* Kafka는 **이벤트 스트리밍**
* 즉각적인 응답 API용 아님

---

## 6. Kafka를 안 쓰면 생기는 문제

### 문제 1: 트랜잭션 지옥

* DB 트랜잭션 + 외부 API
* 하나 느려지면 전부 대기

---

### 문제 2: 장애 전파

* 알림 실패 → 주문 실패
* 분석 서버 장애 → 결제 실패

---

### 문제 3: 확장 불가능

* Application Event는 메모리 기반
* 서버 늘려도 처리 한계 존재

---

## 7. 언제 Kafka를 써야 하는가?

✅ 이런 경우 Kafka를 고려하자

* 이벤트가 여러 서비스로 확장됨
* 트래픽이 급증할 가능성이 있음
* 장애 격리가 중요함
* 재처리가 필요함

❌ 이런 경우는 과함

* 단일 서버
* 단순 CRUD
* 낮은 트래픽

---

## 한 줄 요약 (면접용)

> Kafka는 대규모 트래픽 환경에서
> **이벤트를 안전하게 저장하고,
> 서비스 간 결합도를 끊고,
> 병렬 처리와 장애 복구를 가능하게 하는
